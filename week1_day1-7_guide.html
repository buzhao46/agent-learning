Python 基础速通

必做 · 地基 1.5–2h

今天要拿到什么

产出

out/day1_devices.json + 一个能跑、能报错、能退出的脚本

1
建虚拟环境并装依赖（10 分钟，只做一次）
venv 相当于 Java 的「per-project JDK + Maven 隔离」，不激活就会装到全局。
cd week1
python -m venv .venv
.venv\Scripts\activate          # Windows（macOS/Linux: source .venv/bin/activate）

激活成功的标志：命令行前面出现 (.venv)。
2
读 day1_types.py，重点看这 4 行注释里的映射
Java class → @dataclass；Optional<T> → T | None；checked exception → 自定义异常（Python 不强制 catch）。
@dataclass
class Device:
    name: str
    ip: str
    status: # Literal["up","down"] 等价 Java enum
    tags: list[str] = field(default_factory=list)  # 可变默认值必须这么写

    def is_healthy(self, cpu_limit: int = 80) -> bool:
        return self.status == "up" and self.cpu < cpu_limit
3
跑三条命令，故意触发一次错误
第三条是重点：看它打印友好错误、退出码 2，而不是甩一堆 traceback。
python day1_types.py
python day1_types.py --device core-sw-01
python day1_types.py --device not-exist
echo $?        # Windows: echo %ERRORLEVEL%  → 应为 2

练习（必须动键盘，别只看）

  1. 给 Device 加 uptime: int = 0，输出表增加一列「运行时长」。
  2. 写 load_devices(path) -> list[Device]，把 json 读回对象（提示：Device(**d)）。
  3. 在 main() 里加 time.perf_counter() 计时，结束打印耗时。

验收

会踩的坑

  • tags: list[str] = [] 会让所有实例共享同一个 list，改成 field(default_factory=list)。
  • Windows 上 python 可能指向 Microsoft Store 的假 Python，用 py -3 或全路径。
  • 没激活 venv 就 pip install，包装到全局，后面会找不到模块。

Day 2

asyncio 异步编程

必做 1.5h

今天要拿到什么

理解 await 在哪让出 CPU。巡检 100 台设备，串行 50s、并发 0.5s —— Agent 的并行工具调用全靠它。

产出

一份「串行 vs 并发」耗时对比（脚本自己打印）

1
跑脚本，看 2.5x 提速
python day2_async.py
# 实测：串行 1.52s → 并发 0.61s，提速约 2.5x
python day2_async.py --real    # 额外跑真实 HTTP 并发（需联网）
2
读懂三个关键点
# ① gather 的 return_exceptions=True：一台设备挂掉不拖垮整轮巡检
results = await asyncio.gather(*(fetch(d) for d in devices), return_exceptions=True)

# ② wait_for：到点强制取消，防止 Agent 卡死
await asyncio.wait_for(fetch(d), timeout=2.0)

# ③ Semaphore：限流，别把设备 SNMP 打爆
async with sem:  ...
3
改一处、看一次结果
把 DEVICES 从 3 台加到 10 台，重跑：并发耗时应该几乎不变（只取决于最慢那个），串行会线性变长。这就是你要的直觉。

练习

  1. 给 fetch_health 加 retry：失败重试 2 次，退避 await asyncio.sleep(0.1 * 2 ** i)。
  2. 把 Semaphore(2) 改成 4，观察耗时变化（0.63s → 0.3s 左右）。
  3. 用 httpx.AsyncClient 并发请求 3 个你司内网接口（或 httpbin）。

验收

会踩的坑

  • async def 函数调用后不执行，必须 await 或丢进 gather，否则静默无输出。
  • gather 不加 return_exceptions=True，一台设备超时整轮巡检全挂。
  • 协程里用 requests（同步库）会阻塞事件循环，异步必须用 httpx。

Day 6

项目：LLM 版 Agent

项目日 3.5h

今天要拿到什么

把 minimal_agent.py 的规则决策换成真实模型 Function Calling。这一天过完，你就有第一个能写进简历的 Agent。

产出

可运行的 LLM 版 Agent + out/day6_trace.json

1
先看懂结构，别看代码量（只有四块）
① TOOLS 给模型看的能力清单 → ② TOOL_IMPL 真正干活的函数 → ③ execute_tool 统一入口（异常转 {"error":...}） → ④ run_agent 那个 while 循环。
TOOLS = [{
  "type": "function",
  "function": {
    "name": "get_device_health",
    "description": "查询单台设备的存活状态与 CPU/内存利用率。",   # 写得越清楚，选错概率越低
    "parameters": {"type": "object",
      "properties": {"device": {"type": "string", "description": "如 core-sw-01"}},
      "required": ["device"]}
  }
}]
2
无 Key 先跑规则模式，把 7 步轨迹看懂
python day6_agent_llm.py
# 实测：7 步 / 6 次工具调用，输出 4 条分级诊断
#   [P0] agg-sw-03 离线 → 先查电源/链路/community
#   [P1] core-sw-01 CPU 92% → 查环路/广播风暴
#   [P1] core-sw-01 GE0/0/2 入向错误包 1543 → 疑光衰/误码
#   [P1] core-rtr-02 Gi0/2 down → 查光模块与对端
注意 STEP 2–4：它先把 3 台设备的健康状态查完，才发现 agg-sw-03 离线，于是跳过了它的接口采集。这个「看结果决定下一步」就是 Agent 和脚本的本质区别。
3
配上 Key，切真实模型决策，对比两者的差别
python day6_agent_llm.py
python day6_agent_llm.py --task "只诊断 core-sw-01 这台设备"
python day6_agent_llm.py --max-steps 3    # 验证护栏：到 3 步强制停，防烧钱
真实模式下，调哪个工具、传什么参数是模型自己定的，你只提供 schema 和循环。

改造练习（这三条才是简历素材）

  1. 加高危工具 + 人工确认：写 reboot_port(device, interface)，执行前 input("确认重启？(y/N)")，非 y 返回 {"error":"用户拒绝执行"}。→ 这就是 human-in-the-loop。
  2. 换真实 SNMP：把 tool_get_device_health 函数体换成 pysnmp getCmd（参考 snmp-agent-demo/snmp_client.py），schema 一行不用改。
  3. 并行化：现在「逐台查健康」是串行的，用 Day 2 的 gather 改成并发。

验收（面试官会问的就是这三条）

会踩的坑

  • 回填 assistant 消息时没带 tool_calls，下一轮直接 400。
  • arguments 是字符串，要 json.loads；模型偶尔给非法 JSON，要兜住。
  • 每条 role: tool 消息必须有 tool_call_id，且和上一条一一对应。
  • 没有最大步数护栏，模型会反复调同一个工具，账单很难看。
